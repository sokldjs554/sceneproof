## 무엇을 재나

1. **추론 속도와 결과 차이** (`scripts/gpu_bench.py`): YOLOX nano·tiny·s를 같은 영상 프레임(기본 300장), 같은 전처리·후처리(`edge/detector.py`)로 다섯 가지 방식으로 돌립니다.

   | 방식 | 내용 |
   |---|---|
   | `onnxruntime-cpu` | 기준. 지금 제품 기본값 |
   | `onnxruntime-cuda` | 같은 ONNX를 ONNX Runtime GPU로 |
   | `torch-cuda-fp32` | 원래 PyTorch 가중치를 GPU로 (최적화 전 출발점) |
   | `tensorrt-fp32` / `tensorrt-fp16` | 같은 ONNX로 TensorRT 엔진을 만들어 실행(`TensorRTBackend`) |

   방식마다 추론 시간(p50·p95, 3회 반복), 프레임당 전체 시간(전처리·후처리 포함), 엔진 만드는 시간, 그리고 **CPU 기준과의 차이**를 기록합니다. 차이는 두 단계로 봅니다: NMS 뒤 상자 수가 다른 프레임 수·짝이 안 맞는 상자·상자 좌표 최대 차이(px)·점수 최대 차이, 그리고 NMS 전 신경망 원출력의 최대 차이. GPU가 없거나 설치가 안 된 방식은 멈추지 않고 이유를 남깁니다.

2. **사건 결과가 그대로인가** (`python -m sceneproof.eval.run_eval --backend tensorrt --precision fp16`): 평가 영상 4편을 같은 Colab에서 CPU와 TensorRT FP16으로 각각 분석해 TP·잘못 울림·놓침·중복·시작/종료 오차를 비교합니다. FP16은 숫자를 덜 정밀하게 계산하므로 경계에 걸친 상자 몇 개가 달라질 수 있습니다. 그것이 사건 판정까지 바꾸는지가 실제로 궁금한 점입니다.

## 하지 않는 것

- **Jetson 같은 엣지 장치**: T4는 서버용 GPU라 엣지 장치의 숫자를 대신하지 않습니다. 같은 코드(`TensorRTBackend`)를 Jetson에서 돌리면 엔진만 그 장치에서 새로 만들어집니다(엔진 파일 이름에 GPU 이름과 TensorRT 버전이 들어감).
- **INT8 양자화**: 보정용 영상 세트와 정확도 재측정이 따로 필요해 이번 범위에서 뺐습니다.
- **DeepStream**: Colab에서는 설치가 어렵습니다.
- 여러 영상을 묶어 한 번에 넣는 배치 처리: 제품은 카메라마다 프레임을 하나씩 처리하므로 배치 1로 잽니다.

## 결과 (2차 실행, 2026-11-12)

Colab NVIDIA T4 · CPU 2코어(Xeon 2.0GHz) · TensorRT 11.4 · ONNX Runtime 1.31 · PyTorch 2.14, 코드 `b8b4426`. 원시 결과: `raw/gpu_bench_t4.json`, 사건 평가 `raw/event_eval_yolox_tiny_colab_cpu.json`·`raw/event_eval_yolox_tiny_colab_trt_fp16.json`.

### 1) 추론 속도와 결과 차이

campus-walkway.mp4 300프레임(768×576), 3회 반복의 중앙값. 추론 시간에는 GPU로 보내고 받는 복사가 포함되고, 프레임당 전체 시간에는 CPU에서 하는 전처리(크기 맞추기)와 후처리(겹친 상자 정리)가 더해집니다. '결과 차이'는 CPU 기준과 비교해, 찾은 상자 수가 다른 프레임 수 / 짝이 안 맞는 상자 수(전체 상자 수)입니다.

| 모델 | 방식 | 추론 p50 (ms) | 프레임당 전체 p50 (ms) | 초당 프레임 | 결과 차이 |
|---|---|---|---|---|---|
| nano | CPU (ONNX Runtime) | 17.7 | 20.4 | 47 | 기준 |
| nano | ONNX Runtime GPU | 4.2 | 7.1 | 145 | 0 / 0 |
| nano | PyTorch GPU | 12.3 | 15.1 | 65 | 0 / 0 |
| nano | **TensorRT FP32** | **2.7** | **4.9** | **200** | 0 / 0 |
| nano | TensorRT FP16 | 3.0 | 5.4 | 182 | 2프레임 / 1개 (2,134개 중) |
| tiny | CPU (ONNX Runtime) | 69.0 | 72.4 | 11.5 | 기준 |
| tiny | ONNX Runtime GPU | 4.8 | 7.0 | 141 | 0 / 0 |
| tiny | PyTorch GPU | 11.2 | 14.1 | 66 | 0 / 0 |
| tiny | TensorRT FP32 | 3.5 | 5.7 | 172 | 0 / 0 (한 상자 5.5px) |
| tiny | **TensorRT FP16** | **2.7** | **5.1** | **185** | 3프레임 / 2개 (1,893개 중) |
| s | CPU (ONNX Runtime) | 253.2 | 259.8 | 3.3 | 기준 |
| s | ONNX Runtime GPU | 9.8 | 14.2 | 69 | 0 / 0 |
| s | PyTorch GPU | 12.4 | 17.7 | 51 | 0 / 0 |
| s | TensorRT FP32 | 8.3 | 13.0 | 74 | 0 / 0 |
| s | **TensorRT FP16** | **4.9** | **9.3** | **106** | 1프레임 / 0개 (1,888개 중) |

- **FP32는 결과가 바뀌지 않습니다.** ONNX Runtime GPU, PyTorch GPU, TensorRT FP32 모두 300프레임에서 찾은 상자가 CPU와 같았습니다(원출력 차이 최대 0.0002). tiny TensorRT FP32의 한 상자 5.5px 차이는 같은 사람으로 짝지어진 상자입니다.
- **FP16은 큰 모델일수록 이득입니다.** s는 FP32 대비 1.7배(8.3 → 4.9ms), tiny는 1.3배(3.5 → 2.7ms) 빨라졌습니다. nano는 오히려 조금 느려졌습니다(2.7 → 3.0ms). 계산량이 작아, FP16 모델 앞뒤에 들어가는 형 변환과 FP32로 남긴 크기 조정 연산의 비용이 더 크게 보이는 것으로 짐작합니다.
- **FP16의 대가는 작습니다.** 수천 개 상자 중 0~2개가 달라졌습니다. 신경망 원출력은 상자 좌표 최대 1px, 점수 최대 0.09까지 달라지는데, 0.4 임계값과 겹친 상자 정리를 거친 뒤에는 대부분 사라집니다. 이것이 사건 판정까지 바꾸는지는 아래 2)에서 봅니다.
- **다음 병목은 CPU 쪽입니다.** tiny TensorRT FP16에서 프레임당 5.1ms 중 추론은 2.7ms이고, 나머지 약 2.3ms(약 45%)가 CPU의 전처리·후처리입니다. 더 빠르게 하려면 크기 맞추기와 겹친 상자 정리도 GPU로 옮기거나 다음 프레임과 겹쳐 돌려야 합니다.
- TensorRT 엔진을 처음 만드는 시간은 FP32 약 50초, FP16 약 2~2.5분입니다(모델마다). 한 번 만들면 파일로 저장해 다시 씁니다.
- CPU 숫자는 Colab의 2코어 기준이라 저장소의 4코어 측정(`docs/eval/README.md` §2, tiny 21.6ms)보다 느립니다.

### 2) 사건 결과: CPU vs TensorRT FP16 (평가 영상 4편, 같은 Colab)

| 영상 | 정답 침입 | CPU: 찾음 / 잘못 울림 / 놓침 / 중복 | TensorRT FP16: 찾음 / 잘못 울림 / 놓침 / 중복 | 시작 시각 오차(초) CPU → FP16 | 분석 속도(fps) CPU → FP16 |
|---|---|---|---|---|---|
| campus | 4 | 4 / 0 / 0 / 2 | 4 / 0 / 0 / 2 | 0.23 → 0.23 | 5.0 → 68.9 |
| indoor | 4 | 4 / 0 / 0 / 0 | 4 / 0 / 0 / 0 | 0.20 → 0.20 | 5.4 → 77.2 |
| store | 1 | 1 / 0 / 0 / 3 | 1 / 0 / 0 / 3 | 0.10 → 0.13 | 5.7 → 107.1 |

- **사건 판정은 4편 모두 같았습니다.** 찾음·잘못 울림·놓침·중복이 하나도 바뀌지 않았고, 시작 시각 오차만 매장·주차장에서 0.03~0.06초 움직였습니다(종료 시각 오차는 같음). 상자 몇 개의 차이는 추적과 구역 판정(0.3초 확인)을 거치며 사건에는 드러나지 않았습니다.

- Colab CPU 결과(찾음 12/12, 중복 6)는 저장소의 검수 정답 기준 결과와 같습니다.

### 3) GPU 한 장으로 30fps 카메라 몇 대까지

[![Colab에서 열기](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/sokldjs554/sceneproof/blob/main/notebooks/colab_gpu_channels.ipynb)

현장에서 묻는 숫자는 '프레임 하나에 몇 ms'보다 '장비 한 대로 카메라 몇 대'입니다. 위 2)의 분석 속도에서 나눠 짐작하지 않고, 제품의 분석기(`EdgeAgent`)에 카메라를 실제로 여러 대 붙여서 잽니다(`scripts/gpu_channels.py`, 노트북 [`colab_gpu_channels.ipynb`](../../notebooks/colab_gpu_channels.ipynb)).

**결론부터**: Colab T4(CPU 2코어)에서 1280×720·30fps 카메라를 **기본 설정으로 1대, 근거 프레임을 1초에 10장만 저장하면 2대**까지 기준(모든 채널이 30fps의 98% 이상 분석)을 지켰습니다. GPU 사용률은 그때도 9~19%였습니다 — 채널 수를 정한 것은 GPU가 아니라 CPU 2코어입니다. 처음 잰 1차 실행에서는 한 대도 통과하지 못했고(27.1fps), 프레임이 근거 클립을 인코딩하는 동안 몰아서 버려진다는 것을 찾아 인코더가 분석을 방해하지 않게 고친 뒤 2차 실행에서 위 결과가 나왔습니다. 2차 실행은 인코더를 1차 때 방식으로 되돌린 설정도 같이 재서, 같은 자리에서 0대 → 1대임을 확인했습니다.

#### 측정 방법

- **입력**: 30fps 샘플 영상(worker-zone, 1280×720, 76초)을 카메라 N대인 것처럼 실시간으로 반복 재생합니다. 카메라는 2초 간격으로 시작해 서로 영상의 다른 지점을 보고 있습니다.
- **분석기**: 한 프로세스가 사람 찾기 모델 하나(TensorRT FP16)를 모든 카메라와 같이 쓰고, 카메라마다 영상 읽기 → 대기열(4장, 가득 차면 가장 오래된 프레임을 버림) → 근거 저장 → 추적 → 구역 판정 → 사건 기록이 따로 돕니다. 배포할 때 도는 코드 그대로입니다.
- **통과 기준**(첫 GPU 실행 전에 [`configs/bench/gpu_channels.yaml`](../../configs/bench/gpu_channels.yaml)에 고정): 30초 동안 **모든** 카메라가 30fps의 98% 이상을 분석하면 그 채널 수는 통과. 프레임은 두 군데서 빠질 수 있습니다 — 영상 읽기가 밀리거나, 분석이 밀려 대기열이 프레임을 버리거나. 둘 다 '분석한 프레임 수'가 줄어드는 것으로 잡힙니다.
- **답**: 채널 수 1, 2, 3, 4, 5, 6, 8, 10, 12를 차례로 재서(두 번 연속 실패하면 멈춤) '처음 실패한 채널 수보다 작은, 통과한 가장 큰 채널 수'.
- **비교하는 설정**: 기본값(분석한 프레임을 모두 근거용 JPEG로 저장) / `pipeline.ring_fps: 10`(근거 프레임을 영상 1초에 10장만 저장, [설계 결정 D16](../design/decisions.md)). 1차 실행 뒤에는 '근거 클립 인코더를 1차 때 방식으로 되돌린 것'을 하나 더 넣어, 같은 실행 안에서 수정 전후를 비교합니다(계획 파일에 변경 이력 기록).
- **같이 기록하는 것**: 버린 프레임 수, 분석 지연(p50·p95), CPU·GPU 사용률, 프레임당 단계별 시간(근거 저장·전처리·추론·후처리·추적·구역 판정), GPU 없이 ONNX Runtime CPU로 1·2채널.
- **확인 두 가지**: ① 평가 영상 4편을 한 분석기로 **동시에** 분석한 사건이 한 편씩 분석한 사건과 같은가(카메라들이 모델을 같이 쓰므로, 프레임과 결과가 섞이지 않는지). ② 근거 프레임을 덜 저장해도 사건이 같은가, 근거 사진의 시각과 클립은 얼마나 달라지나(30fps 영상 2편).
- **재지 않는 것**: 1080p 입력(읽기·근거 저장 비용이 더 큼), RTSP 수신(파일 재생으로 대신함), 여러 카메라 프레임을 묶어 한 번에 추론하는 배치 처리, 사람이 수십 명인 장면(추적 비용이 큼), CPU 코어가 많은 장비.

- **인코더 수정의 효과(같은 실행)**: 한 채널에서 버린 프레임 31 → 0장, 지연 p95 165 → 31ms. 두 채널에서는 둘 다 실패지만 합계가 37.3 → 50.3fps가 됐습니다. 한 채널일 때 클립 하나를 쓰는 시간은 2.1 → 2.4초로 거의 같았고(CPU가 남을 때는 늦어지지 않음), CPU가 모자란 두 채널에서는 15초까지 늘었습니다.
- **근거 프레임을 덜 저장한 효과**: 한 채널의 CPU 사용률 64 → 50%, 프레임당 시간 21.6 → 13.2ms. 그 여유로 두 번째 채널이 들어갔습니다. 다만 두 채널은 가장 느린 채널이 98.8%로 기준(98%)을 근소하게 넘었습니다(30초 동안 11장 버림).
- **GPU는 여전히 남습니다**: 두 채널이 통과할 때 19%, 세 채널에서도 23%였습니다. 한 채널의 추론 시간(p50 4.0ms)만 보면 8채널분입니다(계산값).
- 1차 실행 때 방식의 한 채널이 이번에는 29.0fps로, 1차(27.1fps)보다 높았습니다. Colab은 실행마다 받는 기계가 달라(이번에는 CPU만 쓴 숫자도 6.9 → 8.0fps) 실행 사이의 숫자는 그대로 견줄 수 없고, 그래서 전후를 같은 실행 안에서 쟀습니다.
- 확인 ①: 4편을 동시에 분석한 사건 18건이 한 편씩 분석한 것과 같았습니다. 확인 ②: `ring_fps: 10`으로 바꿔도 사건 13건이 같았습니다(1차와 같은 결과).

#### 프레임은 언제 버려졌나 — 근거 클립을 인코딩하는 동안

개발 환경에서 프로세스를 CPU 한 코어에 묶고(작은 CPU 흉내, yolox_nano·ONNX Runtime) 한 채널을 60초 돌리며, 프레임이 버려진 시각과 근거 클립·사진을 쓴 시각을 같이 기록했습니다.

- 버린 프레임 168장 중 **167장이 근거 클립을 쓰는 동안**(끝난 뒤 0.3초 포함) 나왔습니다. 클립은 8개, 하나에 평균 2.1초였습니다(근거 사진을 쓰는 순간과 겹친 것은 그중 4장).
- 클립은 ffmpeg로 H.264 인코딩하는데, 보통 우선순위로 모든 코어를 썼습니다. 코어가 넉넉하면 문제가 없지만 작은 CPU에서는 그 1~2초 동안 분석이 CPU를 뺏겨 대기열(4장)이 넘쳤습니다.
- 고친 것(`edge/evidence.py`): 인코더를 **낮은 우선순위로, 한 스레드로, 프로세스 전체에서 한 번에 하나만** 돌립니다. 같은 조건에서 버린 프레임이 168 → 4장(`ring_fps: 10`이면 0장)이 됐고, 대신 클립 하나를 쓰는 시간이 2.1 → 5.2초로 늘었습니다. 클립이 몇 초 늦게 붙는 대신 분석이 밀리지 않습니다([설계 결정 D17](../design/decisions.md)).

같은 실행 안에서 수정 전후를 비교한 기록(개발 환경, CPU 한 코어, yolox_nano·ONNX Runtime, `raw/gpu_channels_dev_1core_nano.json`; 코드는 `945d122`와 같은 내용이고, 기록 파일에 적힌 `c534418`은 그 커밋을 다른 커밋들 위로 옮기기 전의 번호):

#### 읽는 법과 한계

- 이 결과가 말하는 것은 'T4의 한계가 1~2채널'이 아니라, **이 구성에서는 채널 수가 CPU 코어 수로 정해진다**는 것입니다. Colab의 2코어는 실제로는 한 코어를 둘로 나눈 것(하이퍼스레딩)에 가깝고, 한 채널이 그 50~64%를 썼습니다(2차 실행). 코어가 많은 장비에서 몇 채널인지는 재지 않았습니다.
- 한 프로세스에 카메라를 여러 대 붙이면 파이썬 코드(후처리·추적·구역 판정)는 한 번에 한 스레드만 돕니다. 1차 실행의 두 채널에서 프로세스 CPU가 한 코어 남짓(99~127%)에 머문 것이 그 흔적입니다. 코어가 많은 장비에서는 카메라마다 프로세스를 나누는 편이 맞을 수 있습니다(재지 않음).
- 다음으로 큰 CPU 비용은 근거용 JPEG 변환(Colab에서 프레임당 15~16ms, `ring_fps: 10`으로 5~8ms)과 영상 읽기입니다. 둘 다 GPU(하드웨어 디코더·인코더)로 옮길 수 있는 일이고, DeepStream이 하는 일이기도 합니다(미적용).

측정을 준비하며 고친 것 세 가지(앞의 둘은 카메라가 한 대일 때는 드러나지 않음):

- **TensorRT 동시 호출**: 카메라마다 자기 스레드에서 같은 TensorRT 엔진을 부르는데, 엔진의 입력·출력 버퍼는 하나였습니다. 두 카메라가 겹쳐 부르면 한 카메라의 프레임이 다른 카메라 것으로 덮이고 결과도 바뀌어 읽힐 수 있어, 한 번에 한 카메라만 쓰도록 잠금을 넣었습니다(`TensorRTBackend.run`). ONNX Runtime은 원래 동시 호출이 안전합니다. 위 확인 ①이 GPU에서 이것을 검사했습니다.
- **추적 번호**: 번호를 매기는 카운터를 프로세스의 모든 카메라가 같이 쓰는데 증가가 한 동작이 아니어서, 드물게 한 카메라 안에서 같은 번호가 두 번 나올 수 있었습니다. 증가에 잠금을 넣었습니다(`tracker.STrack.next_id`, 8개 스레드 테스트).
- **오프라인 분석의 근거 클립**: 확인 ②를 만들다 보니 같은 영상을 같은 설정으로 돌렸는데 클립 프레임 수가 471장, 472장으로 달랐습니다. 모든 프레임을 분석하는 오프라인 모드에서는 분석이 영상보다 빨리 나가므로, 클립을 쓰는 사이에 근거 메모리가 그만큼 앞으로 밀려 클립 앞부분이 기기 속도에 따라 잘렸습니다(클립 쓰기를 0.4초 늦추면 201장 → 168장). 오프라인 모드에서는 쓸 차례가 된 클립을 다 쓸 때까지 분석이 기다리도록 해, 실시간으로 돌렸을 때와 같은 근거가 매번 나오게 했습니다(`CameraPipeline._wait_for_due_evidence`, `tests/test_offline_evidence.py`). 사건 판정은 원래 영향이 없었습니다.

### 실행하며 고친 것 (1차 실행, `raw/gpu_bench_t4_run1.json`)

- **TensorRT FP16**: Colab의 TensorRT 11에서는 예전 'FP16으로 만들기' 설정(`BuilderFlag.FP16`)이 없어져 1차에서 실패했습니다. 모델 파일 자체를 FP16으로 바꿔 넣도록 고쳤습니다(`detector.onnx_to_fp16`, 입력·출력은 FP32, 크기 조정 연산은 FP32 유지). TensorRT 10 이하에서는 예전 방식을 씁니다. CPU에서 이 FP16 모델로 100프레임을 돌리면 찾은 사람이 FP32와 같습니다(`tests/test_trt_fp16.py`).
- **사건 평가**: 1차에서는 CPU·GPU 모두 시작하자마자 멈췄습니다. 저장소 의존성이 `protobuf>=5.28`이었는데 생성된 코드는 7.35.1 이상을 요구해, protobuf 6.33이 깔린 Colab에서 실패했습니다. 다른 환경에서도 날 수 있는 실제 결함이라 의존성을 고치고, 다시 어긋나면 실패하는 테스트를 넣었습니다.
- 1차의 FP32 숫자는 2차와 거의 같았습니다(예: tiny TensorRT FP32 3.6 → 3.5ms).
