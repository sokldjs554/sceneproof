# 클러스터에서 평가 실행과 CPU 한도 측정

분석기 Pod의 CPU 한도를 재서 정한 기록입니다. 평가 이미지를 Kubernetes Job으로 돌려 기록된 결과가 그대로 나오는지 확인하고, CPU 한도를 바꿔 가며 실시간 평가를 해서 분석기 설정을 정했습니다.

- **구현:** 저장소 주인이 직접 했습니다. 평가 스크립트의 `--realtime`·`--threads`, 결과에 CPU 한도를 남기는 `provenance.cpu_limit`, kind 클러스터와 Job(`deploy/kind/kind-eval.yaml`, `deploy/k8s/eval/`), 측정 스크립트(`scripts/k8s_cpu_sweep.py`), 코드스페이스 측정, 분석기 설정 결정이 여기에 해당합니다.
- **Claude Code가 준비한 것:** 테스트(`tests/test_eval_realtime.py`), 점검 스크립트(`scripts/check_k8s_eval.sh`), 이 문서입니다.

## 1. 왜 재었나

분석기 Pod의 CPU 한도(요청 1, 한도 2, 추론 스레드 2)는 재서 정한 값이 아니었습니다.

- **오프라인 평가:** 모든 프레임을 분석합니다. CPU가 적으면 느려질 뿐 결과는 같습니다.
- **실시간:** 영상이 제 속도로 흐르고, 분석기가 밀리면 프레임을 버립니다. 이때는 CPU 한도가 결과를 바꿉니다.

## 2. 평가 Job이 클러스터에서 같은 결과를 내는가

GitHub 자동 검사(코어 4개)에서 kind 클러스터를 만들고, 평가 이미지를 Job으로 돌렸습니다. 조건은 오프라인, CPU 한도 2, 스레드 4입니다.

- **결과:** 기록된 결과(`docs/experiments/rerun-20261121/session_base.json`)와 값 291개가 모두 같았습니다. 447초 걸렸습니다. [실행 기록](https://github.com/sokldjs554/sceneproof/actions/runs/45202493272)
- **결과가 남기는 정보:** 결과 파일에 컨테이너가 본 CPU 한도(`environment.cpu_limit`), 이미지를 만든 커밋, 오프라인 여부가 남습니다.
- **Pod 보안:** 네임스페이스는 가장 엄격한 Pod 보안 기준(`restricted`)을 강제합니다. Pod은 노드 폴더를 직접 연결하지 않고, 미리 만든 볼륨(PersistentVolume)으로 결과를 받습니다.

## 3. CPU 한도별 실시간 평가 (코드스페이스, 코어 2개)

조건:
- 코드스페이스(코어 2개)의 kind 클러스터, 평가 이미지 커밋 `255eab5`
- 영상 4편, 프레임 4,002장. 매장 영상은 초당 30프레임, 나머지 3편은 초당 10프레임입니다.
- 한도마다 2번씩 쟀습니다. 스레드는 한도 0.5와 1에서 1개, 2에서 2개입니다.
- 원시 결과: [`raw/k8s_cpu_limits.json`](raw/k8s_cpu_limits.json)와 그 폴더

| CPU 한도 / 스레드 | 버린 프레임 (1회 / 2회) | 찾음 / 놓침 / 잘못 울림 (1회 / 2회) | 사건 F1 (1회 / 2회) |
|---|---|---|---|
| 0.5 / 1 | 2,794 / 2,768 (70% / 69%) | 11 / 1 / 3 · 11 / 1 / 1 | 0.846 / 0.917 |
| 1 / 1 | 1,551 / 1,576 (39% / 39%) | 12 / 0 / 0 · 12 / 0 / 0 | 1.000 / 1.000 |
| 2 / 2 | 1,959 / 1,959 (49% / 49%) | 12 / 0 / 2 · 12 / 0 / 0 | 0.923 / 1.000 |

영상별로 버린 프레임의 비율(1회차)은 다음과 같습니다.

| CPU 한도 / 스레드 | 옥외 보행로 | 실내 | 매장(30fps) | 주차장 |
|---|---|---|---|---|
| 0.5 / 1 | 54% | 58% | 84% | 56% |
| 1 / 1 | 3% | 13% | 68% | 17% |
| 2 / 2 | 21% | 31% | 73% | 28% |

**읽는 법**
- **CPU 0.5:** 프레임의 70%를 버렸고, 사건 1건을 놓쳤으며, 잘못 울림이 1~3건 생겼습니다.
- **CPU 1·스레드 1:** 두 번 모두 사건 12건을 다 찾았고 잘못 울림이 없었습니다. 버린 프레임도 세 조건 중 가장 적었습니다.
- **CPU 2·스레드 2:** CPU 1·스레드 1보다 프레임을 더 버렸습니다(1회 408장, 2회 383장 더). 1회차에는 잘못 울림이 2건 생겼습니다.
- **매장 영상(30fps):** 어느 조건에서도 프레임의 3분의 2 이상을 버렸습니다. 코어 2개로는 이 영상을 실시간으로 따라가지 못합니다.
- **기록된 결과와 다른 값:** 실시간에서는 65~168개가 기록된 결과와 다릅니다. 대부분 사건 번호·추적 번호·시각입니다. 놓침이나 잘못 울림이 생긴 회차(0.5의 두 번, 2의 1회차)는 사건 수 합계도 다릅니다.

## 4. 결정

**분석기 Pod: CPU 요청 1 유지, 한도 2 → 1, 추론 스레드 2 → 1.** 저장소 주인이 결정했습니다(`deploy/k8s/30-edge.yaml`, 커밋 `2db8006`).

이유는 이렇습니다.
- 이 측정에서 1 CPU·1스레드가 가장 적게 버렸고, 두 번 모두 사건을 다 맞혔습니다.
- 요청과 한도가 같아져서, 노드에 다른 일이 몰려도 분석기가 받는 CPU가 흔들리지 않습니다.

## 5. 한계

- **코어 2개에서만 쟀습니다.** 여기서 "CPU 2"는 컴퓨터 전체이고, kind 클러스터 자체 구성 요소와 CPU를 나눠 씁니다. 코어가 많은 장비에서도 1 CPU가 낫다고 말할 수는 없습니다.
- **한도와 스레드를 함께 바꿨습니다.** CPU 2에서 프레임을 더 버린 원인이 한도인지 스레드 2개끼리의 다툼인지는 가르지 못했습니다. 2 CPU·1스레드는 재지 않았습니다.
- **횟수가 적습니다.** 조건마다 2번입니다. 잘못 울림 0~3건의 차이는 우연일 수 있습니다. 같은 조건에서도 F1이 0.923과 1.000으로 갈렸습니다.
- **정답이 4편뿐입니다.** 사건 12건으로 본 결과입니다.
- **추가로 1번 더 잰 결과가 있습니다.** CPU 0.5에서 한 번 더 잰 결과([`raw/k8s_cpu_limits/sweep-wdin7y0n/cpu0.5-run1.json`](raw/k8s_cpu_limits/sweep-wdin7y0n/cpu0.5-run1.json))가 있습니다. 버린 프레임 2,774장, 찾음 12 / 놓침 0 / 잘못 울림 1, F1 0.960입니다.
  - 측정 스크립트를 중간에 고치고 다시 이어서 돌릴 때(`--resume-from`), 가장 먼저 저장한 묶음(`sweep-p7v54lzq`)의 1회차를 읽었습니다. 그래서 이 결과는 요약 표에 들어가지 않았습니다.
  - 지우지 않고 그대로 남겨 둡니다. 이 결과까지 보면 CPU 0.5의 F1은 0.846, 0.917, 0.960입니다.

## 6. 다시 하는 법

```bash
bash scripts/check_k8s_eval.sh /tmp/k8s-eval
```

```bash
bash scripts/k8s_cpu_sweep.sh --limits "0.5 1 2" --runs 2 --out docs/eval/raw/k8s_cpu_limits.json
```

첫 명령은 이미지 빌드, kind 클러스터 생성, 오프라인 Job, 기록과의 비교, 측정 스크립트 짧은 시험, 커밋된 측정 결과 검증까지 합니다. GitHub 자동 검사(`k8s-runtime`의 `eval-job`)에서도 같은 명령이 돕니다. 두 번째 명령은 클러스터 `sceneproof-eval`이 떠 있고 이미지가 들어 있을 때 씁니다.
