# 장애 상황별 동작 (설계 기대치 → 실측은 `docs/evidence/failure-scenarios/`)

| 상황 | 어디서 | 기대 동작 | 운영자가 보는 것 | 검증 |
|---|---|---|---|---|
| 입력이 처리보다 빠름 | 분석기 FrameQueue | 가장 오래된 대기 프레임 폐기, 큐 깊이 ≤ 용량, 지연 상한 유지, 분석 계속 | 카메라 행의 `입력 fps > 처리 fps`, `폐기 프레임` 증가, `분석 지연` | `failure_scenarios.py overload` |
| 스트림 단절·복구 | 분석기 GStreamerSource | 오류/EOS → RECONNECTING, 백오프(0.5→10s) 재접속, 복구 시 STREAMING, 열린 사건은 유예 후 TRACK_LOST로 닫힘 | 카메라 상태 `재연결 중`, `재연결 횟수`, `마지막 오류` | `stream_loss` |
| VLM 지연·실패 | 서버 VLM 워커 | 사건 수신·표시에 영향 없음. 타임아웃·실패는 상태로 기록, 재시도 후 최종 상태 확정, 콘솔에서 재요청 가능 | 사건의 VLM 상태 칩, 상세의 오류 문구, `다시 해석` 버튼 | `vlm_faults` |
| 장치–서버 네트워크 단절 | 게이트웨이 업링크 | DISCONNECTED, WAL에 사건 보존(최신 revision으로 병합), 복구 후 FIFO 재전송, 서버는 `(event_id, revision)`으로 중복 무시 | 업링크 `연결 끊김`, `대기 사건 수`, 복구 후 0으로 감소 | `uplink_loss` |
| 같은 사건 반복 전달 | 서버 upsert | 같은 revision → duplicate ack, 낮은 revision → 무시, 행은 하나 | 사건 목록 중복 없음 | `duplicates` |
| 프로그램 재시작 | 서버·게이트웨이 | SQLite에 사건·검토·해석 보존, running 작업 재큐잉, WAL 재생 | 재시작 전 검토 상태 유지 | `restart` + k8s 검증(pod 삭제) |

## 보존·폐기 정책 요약

| 대상 | 상한 | 가득 찼을 때 |
|---|---|---|
| 분석 대기 프레임 | 4프레임 | 가장 오래된 것 폐기(실시간) / 디코더 블록(오프라인) |
| 근거 링버퍼 | 12초 & 128 MB | 시간 초과분 폐기, 열린 사건 구간은 고정, 바이트 상한은 항상 우선 |
| 분석기 아웃박스 | 512 사건 | 가장 오래된 것 폐기(게이트웨이가 죽어 있는 동안만 사용) |
| 게이트웨이 WAL | 64 MiB | 가장 오래된 대기 사건 퇴거(DROP 기록), 카운터 노출 |
| 게이트웨이 업로드 | 10분 재시도 창 | 포기하고 로그·카운터 |
| 서버 VLM | 동시 1, 호출 90s, 2회 시도, 예산 $5 | timeout/failed/skipped 상태로 기록 |
