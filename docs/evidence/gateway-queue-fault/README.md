# 게이트웨이 디스크 큐: 쓰기가 실패한 뒤 받은 사건이 사라지는 결함

게이트웨이의 디스크 큐(`gateway/internal/queue`)에서 찾은 결함과, 큐를 다시 구현해 없앤 기록입니다.

- **결함을 찾고 재현 테스트를 쓴 것:** Claude Code (2026-11-24, 커밋 `eab3df6` 기준)
- **큐를 다시 구현하고 결함을 없앤 것:** 저장소 주인. 원래 코드를 보지 않고 명세(`gateway/README.md` 3~4절)와 테스트만 보고 작성했습니다(커밋 `dc256d8`, `3125156`).

## 결함

- 큐는 레코드를 파일 끝에 이어 붙입니다. 재시작하면 파일을 처음부터 읽다가 믿을 수 없는 레코드를 만나면 거기서 멈추고 그 뒤를 잘라 냅니다.
- 디스크가 가득 차면 쓰기가 레코드 중간에서 멈출 수 있습니다. 원래 코드는 이때 오류를 돌려주지만, 파일에 남은 반쪽 레코드는 그대로 둡니다.
- 디스크에 자리가 다시 생기면 다음 사건은 그 반쪽 레코드 뒤에 정상으로 기록되고, 분석기는 `accepted=true`를 받습니다.
- 재시작하면 복구가 반쪽 레코드에서 멈춥니다. 그 뒤에 받은 사건은 전부 잘려 나갑니다. "받았다고 답한 사건은 서버가 확인할 때까지 남는다"는 약속이 깨집니다.

## 재현

원래 코드는 파일을 `os.OpenFile`로 직접 열어서 쓰기 실패를 흉내 낼 수 없습니다. 그래서 파일 여는 함수를 바꿔 끼울 수 있게만 고친 사본(`seam.patch`, 동작은 그대로)에 장애 주입 테스트(`gateway/internal/queue/queue_fault_test.go`)를 돌렸습니다. 결과는 `before.txt`입니다.

| 테스트 | 원래 코드 |
|---|---|
| 쓰기가 중간에 실패한 뒤 받은 사건이 재시작 후 남는가 (실패 지점 9가지) | 8가지 실패. 0바이트만 쓰인 경우만 통과 |
| 확인(ACK) 기록이 실패한 뒤에도 파일이 온전한가 | 실패 |
| 무작위 장애 300단계 × 40회에서 받은 사건을 잃지 않는가 | 40회 중 31회 실패 |
| 그 밖의 테스트(형식, 복구, 압축, 동시 사용) | 통과 |

`seam.patch`에는 원래 코드가 몇 줄 들어 있습니다.

## 다시 구현한 뒤

같은 테스트를 새 구현에 돌린 결과는 `after.txt`입니다.

| 테스트 | 원래 코드 | 새 구현 |
|---|---|---|
| 쓰기가 중간에 실패한 뒤 받은 사건이 재시작 후 남는가 (실패 지점 9가지) | 8가지 실패 | 9가지 모두 통과 |
| 확인(ACK) 기록이 실패한 뒤에도 파일이 온전한가 | 실패 | 통과 |
| 무작위 장애 300단계 × 40회 | 31회 실패 | 40회 모두 통과 |

이 밖에 다음 검사도 모두 통과했습니다.

- 큐 테스트 19개: 기존 6개 + 장애 주입 + 파일 형식 + 이전 버전 파일 + 모든 지점 자르기 + 동시 사용
- 게이트웨이 전체 테스트(`go test -race`)
- 퍼즈 테스트 2개, 각 30초

**고친 방법:**
- 큐는 "마지막으로 온전하게 쓴 위치"(`committedBytes`)를 따로 기억합니다.
- 쓰기나 fsync가 실패하면, 다음 기록을 쓰기 전에 파일을 그 위치로 잘라 되돌립니다.
- 자르기마저 실패하면 그 뒤의 쓰기도 모두 실패로 답합니다. 반쪽 기록 뒤에 새 사건을 붙이지 않기 위해서입니다.
- 사건 기록(PUT)과 그 때문에 밀려나는 사건의 기록(DROP)은 한 묶음으로 씁니다. 하나라도 실패하면 묶음 전체를 되돌리고, 메모리는 다 쓴 뒤에만 바꿉니다.

**원래 코드와 달라진 동작:**
- 새 revision이 커서 그 사건 자신이 밀려나는 드문 경우, 원래 코드는 `accepted=true`로 답하고 사건을 버렸습니다. 이제는 `accepted=false`로 답합니다.
- `MaxBytes`가 음수이면 기본값 대신 오류를 냅니다.
- 압축할 때 받은 바이트를 그대로 다시 씁니다. 지금 버전이 모르는 필드도 지워지지 않습니다.
- 파일 형식은 그대로라 이전 버전이 쓴 파일이 열립니다(`testdata/v1.wal`).
