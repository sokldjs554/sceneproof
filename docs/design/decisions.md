# 설계 결정과 대안

각 항목은 "결정 — 대안 — 이유 — 확인 방법" 순서입니다. 코드 위치를 같이 적었습니다.

## D1. 탐지기: YOLOX(Apache-2.0) + 자체 ONNX 내보내기
- 대안: Ultralytics YOLOv8/11(AGPL-3.0, 내장 추적기·export), torchvision SSDLite(BSD, 정확도 낮음), RT-DETR(무거움).
- 이유: 상용 회사 지원용 포트폴리오에서 라이선스는 설계 판단의 일부입니다. YOLOX는 Apache-2.0이고, 모델 코드 5개 파일만 벤더링(`src/sceneproof/edge/yolox_model/`)하면 PyTorch 경로와 ONNX 경로를 **같은 전·후처리**로 비교할 수 있습니다. CPU 4코어에서 tiny가 416 입력 기준 p50 ≈ 21 ms로 30 fps 입력을 처리합니다(`docs/eval/README.md`).
- 확인: `scripts/export_onnx.py`가 내보내기 직후 무작위 입력으로 원시 출력 최대 오차(1e-5 수준)를 기록, `tests/test_detector.py::test_torch_and_onnx_backends_agree`가 실제 프레임에서 NMS 후 상자 일치를 검사.

## D2. 추적기: ByteTrack 자체 구현 (`src/sceneproof/edge/tracker.py`)
- 대안: `supervision`/`boxmot` 라이브러리, 간단한 IoU 추적.
- 이유: 구역 체류 시간은 ID가 안정적일 때만 의미가 있습니다. ByteTrack의 핵심(저신뢰 상자를 2차 연계에 사용)은 ~250줄로 구현 가능하고, 직접 구현해야 `track_buffer`·2단계 임계값·가림 시 ID 유지 같은 동작을 테스트로 고정할 수 있습니다(`tests/test_tracker.py`: 가림 중 저신뢰 상자로 ID 유지, 버퍼 내 재출현 시 ID 복원, 교차 시 ID 구분).
- 차이: 헝가리안(scipy)에 비용 게이트를 둔 방식이라 원 구현의 lapjv와 동률 처리에서 드물게 다를 수 있습니다.

## D3. 구역 판정 앵커 = 상자 하단 중앙(발) (`zones.anchor_point`)
- 대안: 상자 중심, 상자-다각형 겹침 비율.
- 이유: 구역은 바닥에 그린 다각형입니다. 상체가 구역 위에 겹쳐도 발이 밖이면 침입이 아닙니다.
- 한계(평가에서 확인): 선반·물건에 발이 가리면 상자 하단이 발이 아닙니다(`eval-store`, `occluded` 라벨). 상자가 프레임 하단에 걸리면 앵커가 프레임 가장자리가 됩니다 → **상태 유지**로 처리(`box_clipped_at_bottom`, `tests/test_zones.py::test_box_clipped_at_frame_bottom_holds_state`). 이 버그는 캠퍼스 영상에서 한 사람의 체류가 4개 사건으로 쪼개지는 것을 보고 찾았습니다(`docs/dev-log.md`).

## D4. 디바운스는 프레임 수가 아니라 초 단위 (`ZoneSpec.entry/exit_confirm_seconds`)
- 처음에는 프레임 수(진입 3, 이탈 5)로 구현했습니다. 30 fps 영상에서 이탈 확정 8프레임은 0.27초라 깜빡임마다 사건이 쪼개졌습니다(`eval-store` 초안 #2/#3, #5/#6). 미디어 시간 기준으로 바꾸고 프레임 수는 하위 호환으로 남겼습니다.

## D5. 사건은 스냅샷 + revision; 큐는 병합 가능 (`proto`, `gateway/internal/queue`)
- 대안: 증분 이벤트(opened/dwell/closed 각각 별도 메시지).
- 이유: 증분 이벤트는 순서·누락에 취약합니다. 스냅샷이면 서버는 `(event_id, revision)` 비교만으로 멱등하고, 게이트웨이는 오프라인 동안 쌓인 같은 사건의 오래된 revision을 버려도 됩니다. 중복 전달·재시작·재전송이 모두 같은 규칙으로 처리됩니다(`scripts/failure_scenarios.py::sc_duplicates`).

## D6. 게이트웨이를 Go로, 분석기와 분리
- 대안: Python 분석기 안에서 직접 서버로 전송.
- 이유: 내구 큐·재연결·업로드는 영상 처리와 수명이 다릅니다(분석기 재시작·모델 교체와 무관하게 전송은 계속돼야 함). Go는 정적 바이너리·goroutine으로 이런 데몬에 맞고, 공고의 "Python 외 C/Go" 요건을 실제 책임이 있는 모듈로 채웁니다. 경계는 gRPC 계약 하나(`EdgeIngress`)입니다. 상세: [`gateway/README.md`](../../gateway/README.md).

## D7. VLM은 서버에서, 비동기로, 범주형 출력만 (`server/vlm/*`)
- 대안: 엣지에서 VLM 실행, 동기 호출, 자유 텍스트 출력.
- 이유: VLM은 느리고(수 초~수십 초) 실패합니다. 사건 기록·CV 근거는 VLM과 무관하게 먼저 저장되고, 해석은 큐에서 처리됩니다(타임아웃·재시도·예산 상한). 출력은 JSON 스키마로 검증하고 확률·신뢰도 필드를 두지 않습니다. 모의(mock) 제공자는 결과에 `[MOCK]`을 박고 품질 수치로 보고하지 않습니다.
- 제공자 추상화: Anthropic(Claude) / OpenAI 호환(vLLM·llama.cpp) / transformers 로컬(SmolVLM) / mock. 어떤 것을 실제로 돌렸는지는 `docs/eval/README.md`에 적습니다.
- 실측으로 확인(2026-11-08, Claude Opus 5.5, 평가 19건): 정답 침입 10건 중 3건을 모델이 `likely_benign`으로 판단했습니다. VLM 판단을 자동 종결 게이트로 썼다면 이 3건은 사람 눈에 띄지 않았을 것입니다. 보조 표시로만 쓰고 기본 상태를 '확인 필요'로 두는 이 결정은 유지합니다. 규칙을 명시한 프롬프트 v1.3에서는 10건 중 8건 '확인 필요'·'정상' 0건으로 바뀌었지만, 경계 통과도 '확인 필요'로 밀려 올라가 검토 대상이 줄지는 않았습니다(`docs/eval/vlm-findings.md`).

## D8. 링버퍼와 프레임 큐의 정책 분리 (`frames.py`)
- 프레임 큐: 분석이 늦으면 **가장 오래된 프레임 폐기**(실시간성 우선). 오프라인 평가는 무손실 모드(재현성 우선).
- 링버퍼: 근거를 위해 최근 N초를 보관, 열린 사건의 pre-roll은 **고정(pin)**, 다만 바이트 상한이 최종 우선. 두 버퍼의 목적이 달라 정책도 다릅니다.

## D9. 저장소: SQLite(WAL)
- 대안: PostgreSQL.
- 이유: 단일 서버·단일 작성자 데모에 충분하고 재시작 복구·멱등 upsert를 한 파일로 검증할 수 있습니다. k8s에서는 `Recreate` 전략 + RWO PVC로 작성자 하나를 보장합니다. 다중 서버는 범위 밖(한계 문서).

## D10. 콘솔은 빌드 없는 정적 파일
- 대안: React/Vite.
- 이유: 공개 데모·오프라인 실행·Pages 정적 재생을 같은 파일로 하기 위해서입니다. 상태는 서버가 가지고 콘솔은 2초 폴링으로 동기화합니다.

## D11. 연구용 벤치마크: 정답 사건은 사람이 그린 상자에서 '같은 규칙'으로 만든다 (`eval/bench/*`)
- 문제: 처음 평가는 영상 4편·사건 19건이고 정답을 Claude가 초안으로 만들어, "대체로 이 정도"라고 말할 근거가 없었습니다.
- 결정: 사람이 프레임마다 손으로 그린 사람 상자가 있는 연구용 공개 데이터(CAVIAR, MOT16/20 정지 카메라 84편, 뒤에 두 번째 최종 분할용 MOT20 2편 추가)를 쓰고, 사건 정답은 그 상자를 **제품의 ZoneMonitor에 그대로 통과**시켜 만듭니다. 정답과 예측의 차이가 "상자를 누가 그렸나" 하나만 남습니다. 사건 시각을 사람이 따로 적는 방식보다 장소·구역이 바뀌어도 다시 만들 수 있고, 구역 규칙(확정 시간·체류 기준)을 바꾸면 정답도 같은 규칙으로 따라옵니다.
- 맞음 판정: 시간 겹침만으로는 혼잡한 장면에서 다른 사람의 사건으로 점수를 받습니다. 같은 순간의 발 위치 차이가 키의 절반 이하일 때만 같은 사람으로 봅니다.
- 공정성: 분할(학습/조정/최종)을 구역을 그리기 전에 고정·커밋하고(내용 해시로 사후 수정 감지), 구역은 학습·조정 영상만 보고(처음 보는 장소는 첫 화면만 보고) 그렸으며, 최종 분할은 후보 모델 목록을 고정한 뒤 잠금 파일로 한 번만 잽니다. 다시 재려면 이유를 남겨야 합니다.
- 한계: 데이터 정답이 사람이 그렸어도 '사건' 기준은 이 프로젝트의 규칙입니다. 두 사람이 사건을 따로 표시해 일치도를 재는 도구(`tools/event_labeler`, `agreement.py`)를 만들었지만 실제 표시는 사용자 몫입니다. 몇 시간짜리 영상의 시간당 잘못 울림은 사람이 표시한 연구용 데이터가 없어(동의서가 필요한 VIRAT 제외) 사용자가 직접 찍은 영상과 확인 도구(`idle_review.py`)로 재는 방법을 남겼습니다.

## D12. 사람 찾기 모델 추가 학습은 CPU로, 같은 계열 모델 안에서
- 근거: 조정 분할에서 위에서 내려다보는 로비 화면의 사람을 기본 모델이 거의 못 찾았습니다(사람 찾기 AP50 0.05). 3배 큰 COCO 모델로 바꾸면 조금 낫지만 매장 정면 화면에서 잘못 울림이 4배 넘게 늘었습니다.
- 결정: 제품과 같은 YOLOX-tiny를 학습 분할의 사람 상자로 추가 학습(원본 학습 손실 SimOTA를 벤더링, 데이터 증강은 크기·위치·좌우·색상만). GPU 없이 4코어 CPU로 10회차 약 1.7시간. 회차는 조정 분할의 사람 찾기 AP로 고르고, ONNX로 내보내 제품과 같은 추론 경로로 평가합니다.
- 이유: 모델 크기·입력 형식·후처리를 그대로 두면 배포(엣지 CPU 속도, ONNX Runtime 경로)를 바꾸지 않고 가중치 파일만 교체하면 됩니다.
- 조건: 학습 데이터에 비상업(CC BY-NC-SA) MOT16이 들어가 추가 학습 가중치는 비상업·연구 용도입니다(`THIRD_PARTY_NOTICES.md`).

## D13. 구역 판정 보정은 '애매하면 하지 않는다', 놓침을 늘리는 설정은 기본값으로 두지 않는다 (`edge/zones.py`, `configs/edge.yaml`)
- 근거: 추적 번호가 바뀌어 사건이 쪼개지는 문제를 위치만으로 이어 붙이자(이어받기) 한산한 조정 분할에서는 좋아졌지만, 처음 보는 아주 붐비는 장면에서 다른 사람에게 사건을 넘겨 잘못 울림이 5→26건으로 늘었습니다(두 번째 최종 측정). 새 추적 시작 점수를 올리는 설정은 중복을 약 40% 줄였지만 놓침이 약 1% 늘었습니다.
- 결정: 이어받기는 보이는 사람이 정확히 한 명이고 그 사람이 구역 안의 새 추적일 때만 합니다(기본 꺼짐, 켜도 붐비는 곳에서는 거의 동작 안 함). 추적 설정은 놓침이 가장 적은 기본값을 유지하고, 붐비는 현장은 카메라별 `tracker` 블록으로 고릅니다. 사람 모양 물체는 설치 때 제외 영역으로 그립니다(사건을 열지 않되 열린 사건은 유지 — 실제 사람이 지나가도 끊기지 않게).
- 이유: 이 제품의 목적은 출입 안전이라 놓친 출입이 중복보다 비쌉니다. 중복은 검토자가 한 번 더 보면 되지만 놓친 출입은 아무도 보지 못합니다.
- 남은 것: 아주 붐비는 장면에서 같은 사람을 끝까지 같은 번호로 따라가려면 겉모습을 비교하는 추적이 필요합니다(GPU 전제).

## 채택하지 않은 기술

| 기술 | 결정 | 이유 | 남은 검증 |
|---|---|---|---|
| MQTT | 미적용 | 사건은 ack·멱등이 필요해 gRPC 단일 계약으로 충분. 상태·명령도 같은 연결(WatchCommands)로 해결 | 브로커 기반 다수 장치 팬인 |
| DeepStream / Jetson / TensorRT | 설정·경로만 준비 | 이 세션에 NVIDIA 장비 없음. ORT 백엔드의 `providers` 설정으로 TensorRT EP를 지정할 수 있게 해 두었음 | 장비에서 실행·측정 |
| vLLM | 클라이언트 경로만 | CPU 환경. OpenAI 호환 제공자로 `vllm serve <VLM>`에 바로 연결 가능 | GPU에서 실행·지연 측정 |
| Kubernetes(로컬) | CI(kind)에서 검증 | 이 세션 샌드박스에서는 중첩 런타임 제약으로 파드 기동 실패(`docs/evidence/k8s-local-attempt/`) | CI 실행 결과 확인 |

## D14. 동시에 구역 안에 있던 사건은 '합치지 않고 묶어 보여준다' (`server/groups.py`, 콘솔 목록·처리 상태 탭)
- 문제: 제품은 사람마다 사건을 만든다(정답 규칙과 같음). 두 사람 표시 일치도 2차에서 사람은 함께 있는 무리를 사건 하나로 셌고, 매장 영상처럼 2~3명이 함께 들어오면 담당자가 같은 상황의 알림을 여러 번 열어야 한다. 한 사람의 추적 번호가 바뀌어 둘로 나뉜 사건도 시간이 겹친다.
- 결정: 같은 카메라·같은 구역에서 영상 시간과 실제 시각이 모두 겹치는 사건을 한 묶음으로 표시한다(겹침이 이어지면 같은 묶음). 실제 시각까지 보는 이유는 같은 영상을 다른 때 다시 분석한 결과를 묶지 않기 위해서다. 목록에서는 묶음이 **펼친 상태로** 시작하고(접을 수 있음), 처리 상태 탭에서 묶음 전체를 한 번에 검토 시작·처리 완료할 수 있다. 처리는 사건마다 따로 기록되고 메모에 묶음 처리였다는 사실이 남는다.
- 하지 않은 것: 사건을 하나로 합치기. 합치면 사람 수·체류 시간·근거 프레임이 사람마다 달라 정보가 사라지고, 정답 비교(사람마다 한 건)가 깨진다. 묶음을 접은 채 시작하지 않는 이유도 같다 — 알림을 기본으로 숨기지 않는다(D7).
- 확인: 단위 테스트(`tests/test_groups.py`, `tests/test_server.py`), 매장 영상 재생으로 4건 묶음 → 묶음 검토 시작 → 묶음 처리 완료를 브라우저에서 확인(오류 0, 사건마다 이력 2줄). 화면: `docs/images/console-concurrent-group.png`.
- 추가(2026-11-13): ① 거의 이어진 사건(추적 번호가 바뀌어 잠깐 끊긴 경우)까지 묶는 `gap_s` 옵션. 기본 0(기존과 같음)이고 API·화면에는 연결하지 않았다 — 값을 크게 주면 연결이 이어져(A–B, B–C, C–D…) 긴 시간 전체가 한 묶음이 될 수 있어 기본으로 켜지 않는다. ② 사건 목록 API의 `concurrent_only`: 묶음을 **전체 사건으로 먼저 계산한 뒤** 처리 상태 조건과 페이지를 적용해, 거르거나 나눠도 묶음 정보가 유지된다(`tests/test_api_concurrent_only.py`). 대가는 요청마다 전체 사건을 읽는 것이다(합성 사건 5,000건에서 67 → 503ms, `docs/eval/raw/api_event_list_bench.json`). 기본 목록은 여전히 돌려주는 행 안에서만 묶으므로 '확인 필요'만 걸러 보면 묶음 정보가 줄거나 사라진다(같은 측정에서 837건 중 381건). 두 조회의 기준을 맞추고, 요청 범위 근처만 읽거나 수집 때 묶음을 저장하는 것이 남은 일이다(이어지는 묶음과 진행 중 사건을 유지해야 한다).

## D15. 작은 사람 상자를 무시하는 기능은 설정으로 두고 기본은 끈다 (`edge/detector.py`의 `min_box_height_px`)
- 문제: 아주 멀리 있는 사람의 작은 상자를 현장에 따라 무시하고 싶을 수 있다.
- 결정: 겹친 상자 정리(NMS) **뒤에** 기준 높이(px)보다 낮은 상자를 빼는 설정을 두되 기본은 0(끔). NMS 앞에서 거르면 작은 상자가 억제하던 큰 상자가 살아남아 결과가 달라질 수 있다. 음수는 설정 단계에서 거부하고, 값은 실행 기록(`DetectorInfo`)에 남겨 나중에 결과를 볼 때 켜져 있었는지 알 수 있게 한다.
- 근거: 평가 영상 4편에서 40px로 켜도 찾음·놓침·중복은 같았지만 주차장 영상의 종료 시각이 달라졌고, 기본 3회·40px 2회 반복 실행에서 같은 차이가 재현됐다. 주차장 표본에서 40px 미만 상자 5개는 모두 화면 위쪽 가장자리에 닿아 있었다 — 픽셀 하나로 자르면 '멀리 있는 사람'뿐 아니라 '화면 밖으로 나가는 사람'도 지울 수 있다(어떤 상자가 종료 시각을 바꿨는지까지는 추적하지 않음; `docs/experiments/min-box-height-20261113/`).
- 한계: 픽셀 기준은 해상도와 거리에 따라 다르게 작동한다. 화면 높이 대비 비율이나 화면 위치별 기준이 다음 후보다.
