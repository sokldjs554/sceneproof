# 개발 기록 — 발견한 실패, 원인, 수정 전후

커밋 해시는 `git log`로 확인할 수 있습니다. 각 항목은 "문제 → 원인 → 수정 → 전후 비교 → 확인 방법"입니다.

## L1. GStreamer 파일 재생이 4초에 2프레임만 전달
- 문제: `filesrc ! decodebin ! … ! appsink sync=true drop=true max-buffers=2`로 60초 영상을 열면 6초 동안 프레임 2장만 콜백됨.
- 원인: `sync=true`(클록 동기)와 `drop=true`를 함께 쓰면 디코더가 실시간보다 앞서 가며 appsink가 "지금 렌더할" 버퍼를 계속 더 새 버퍼로 교체한다. 렌더 시각이 영원히 뒤로 밀린다.
- 수정: 파일 소스는 `drop=false`(디코더가 싱크에 블록되어 자연스럽게 페이싱), 라이브 RTSP는 `sync=false drop=true`(RTP 경로를 막지 않고 오래된 디코드 프레임만 버림). `sources.py` 주석.
- 전후: 2 프레임/4s → 1340 프레임/4s(sync=false) · 실시간 페이싱 정상.

## L2. 오프라인 분석에서 1394 프레임 중 1360 프레임 폐기
- 문제: 평가용 오프라인 실행이 실시간 폐기 정책을 그대로 써서 디코더가 분석기보다 빨라지자 거의 모든 프레임을 버림(사건 0개, 근거 클립 없음).
- 원인: "실시간 우선"과 "재현성 우선"은 다른 정책인데 큐가 하나의 정책만 가짐.
- 수정: `FrameQueue(lossless=True)` — 생산자를 블록. `realtime=False`(오프라인/평가)일 때 자동 선택. 라이브는 그대로 폐기 정책.
- 전후: 34/1394 처리 → 1394/1394 처리, 사건 6개·클립 6개(`cam-bench`).

## L3. 한 사람의 체류가 4개 사건으로 쪼개짐 (프레임 하단 클리핑)
- 문제: 캠퍼스 평가 초안에서 track 29가 53.4–75.5초 잔디 위에 있었는데 사건이 4개(53.4–58.0, 59.0–60.0, 61.1–62.0, 62.5–75.5)로 생성됨.
- 원인: 사람이 화면 하단에 걸리면 상자 하단(y2)이 프레임 끝이 되고 앵커 y=1.0은 다각형(아래 변 y=1.0) **밖**으로 판정(ray casting 경계 규칙). 발이 보이지 않는 상황을 "밖"으로 해석한 것이 잘못.
- 수정: `box_clipped_at_bottom` — 상자가 하단에 닿으면 안/밖을 세지 않고 상태를 유지(열린 사건은 유지). 테스트 `test_box_clipped_at_frame_bottom_holds_state`.
- 전후: 평가 결과(`docs/eval/README.md`)의 `duplicates` 열에서 확인 — 수정 전 초안(yolox_s)은 같은 정답에 중복 3건.

## L4. 30fps 영상에서 이탈 확정이 0.27초
- 문제: 매장 영상(30fps)에서 50.2–50.8초, 65.1–65.3초 같은 짧은 깜빡임마다 사건이 닫히고 새로 열림.
- 원인: 디바운스를 프레임 수로 설정(이탈 8프레임). 10fps에서는 0.8초지만 30fps에서는 0.27초.
- 수정: `entry_confirm_seconds` / `exit_confirm_seconds`(미디어 시간 기준)를 추가하고 설정 기본값을 0.3s/0.8s로 통일. 프레임 수는 하위 호환 fallback. 테스트 `test_time_based_debounce_is_fps_independent`.

## L5. 명령이 두 번 도착하면 파이프라인을 두 번 재시작
- 문제: 콘솔에서 "분석 시작"을 두 번 누르자(또는 게이트웨이가 버퍼링한 명령을 재전달하자) 같은 카메라가 재시작되어 사건이 끊김.
- 원인: START가 멱등이 아니었음.
- 수정: 같은 소스로 이미 실행 중이면 no-op("already running"). 소스가 다르면 재시작.

## L6. SQLite `executescript`는 트랜잭션 안에서 못 씀
- `BEGIN IMMEDIATE` 안에서 스키마 스크립트를 실행하면 "cannot commit - no transaction is active". `executescript`는 자체적으로 커밋하므로 autocommit 모드에서 호출.

## L7. 상대 경로 `file://` URI
- `urlparse("file://data/videos/x.mp4")`는 `data`를 호스트로 해석. 설정 편의를 위해 `file://` 접두어는 단순 제거로 처리하고 문서화.

## L8. 선반에 가린 발 (한계로 기록)
- 매장 영상에서 통로 중간 사람의 상자 하단은 접시 더미 위 — 지면 위치가 아님. 앵커 방식의 구조적 한계이며, 정답에서는 `occluded`로 분리해 TP/FP에서 제외. 해결 방향: 바닥 호모그래피 + 키포인트(발목) 또는 구역을 가림이 없는 영역으로 설계.

## L9. 타임아웃된 VLM 호출의 결과가 뒤늦게 상태를 덮어씀 (장애 시나리오에서 발견)
- 문제: `vlm_faults` 시나리오(mock 3초 지연, 타임아웃 1.5초)에서 "timed out; re-queued" 직후 같은 작업이 "done"으로 바뀜. 이미 타임아웃 처리된 호출의 스레드가 3초 뒤 끝나며 결과를 써 버렸다.
- 원인: `asyncio.wait_for`는 executor 스레드를 취소하지 못한다. 늦게 끝난 스레드를 막는 장치가 없었다.
- 수정: 시도 번호(attempts)를 토큰으로 사용. 작업을 시작할 때 attempts를 올리고, 결과를 쓰기 전에 DB의 (status=='running', attempts==내 토큰)을 확인. 아니면 결과를 버린다. 회귀 테스트 `test_slow_provider_times_out_and_late_result_is_discarded`.

## L10. '실행 중(running)'이 대기 중 작업까지 포함
- 문제: 동시성 1인데 콘솔에 `running: 14`로 표시. 루프가 큐에서 꺼낸 작업을 세마포어 대기 전에 모두 running으로 표시했다.
- 수정: 여유 용량만큼만 꺼내고, 실제 실행하는 태스크만 running으로 표시(`_loop`/`_run_job_task`). 시나리오의 "큐·실행 중 작업이 영원히 남지 않음" 검사가 통과.

## L11. 시나리오 하네스 자체의 버그
- protobuf JSON은 int64를 문자열로, 0 값은 생략해 직렬화한다 → `dropped_frames > 0` 비교가 TypeError. 정규화 함수 추가.
- 서버를 내린 뒤 API를 조회해 결과가 비어 보였던 문제(수집 순서), RTSP 시뮬레이터 포트가 열리기 전에 분석기를 띄운 문제(포트 대기) 수정. 하네스 버그와 시스템 버그를 구분해 기록.

## L12. Claude 호출이 `stop_reason=max_tokens`로 잘림 (CI vlm-eval #3에서 발견)
- 문제: 키 인증은 통과했는데 첫 실제 해석이 출력 1024토큰에서 끊겨 JSON이 비어 있었다(`no JSON object found`).
- 원인: Claude Opus 5.5는 thinking을 끌 수 없고 thinking 토큰이 `max_tokens`에 포함된다. 제공자가 `max(req.max_tokens, 1024)`로 상한을 잡아 thinking만으로 예산이 소진됐다.
- 수정: 제공자 하한 4096(`MIN_MAX_TOKENS`), 설정 기본값 `vlm_max_tokens=4096`, `vlm_effort` 노출. 실제 호출의 출력은 건당 평균 약 2천 토큰(thinking 포함)이었다. 비용 추정에 캐시 쓰기·읽기 토큰도 포함하도록 고침.
- 같이 발견: 잘못된 API 키는 유료 호출 전에 걸러야 한다 → 워크플로 스모크 단계에서 키 유형·공백 검사와 무료 `GET /v1/models` 인증 확인을 먼저 수행.

## L13. CV 결과와 VLM 해석의 조인이 전부 'unmatched' (CI vlm-eval #4에서 발견)
- 문제: 해석 19건이 모두 완료됐는데 `정답 침입 유지 0/0`처럼 비교 지표가 비어 있었다.
- 원인: 사건 ID는 `(카메라, 구역, 트랙, 진입 프레임)`의 uuid5라서 같은 영상이라도 기기(CPU 부동소수 차이 → 탐지·트랙 ID 변화)가 다르면 달라진다. `vlm_eval.py`가 샌드박스에서 만든 이전 `event_eval_*.json`의 ID로 조인해 CI 실행과 하나도 맞지 않았다.
- 수정: 서버에 재생한 **같은 실행의** `events.jsonl`을 정답 YAML과 직접 매칭(`--events-jsonl`, 매칭 규칙은 사건 평가와 동일)하고, 결과 JSON에 `matching` 블록(매칭/미매칭 수, CV 결과별 분포)을 기록. 전부 미매칭이면 경고를 출력. 로컬 재생 테스트(eval-campus, mock 제공자)에서 5/5 매칭 확인 후 CI 재실행.
- 교훈: "결정적 ID"는 같은 입력·같은 수치 결과를 전제로 한다. 실행 간 비교는 ID가 아니라 시간 구간 매칭으로 해야 한다.

## L14. 유료 실행 뒤의 '결과 커밋백'이 두 가지 이유로 실패 (CI vlm-eval #6–#8)
- 다운로드: 샘플 영상을 `github.com/<repo>/raw/…` 리디렉션 엔드포인트에서 받았는데 30초 넘게 504가 이어졌다(재시도 6회도 소용없음). `raw.githubusercontent.com`에서 직접 받고 github.com은 대체 경로로 돌렸다. 두 번 모두 유료 호출 전에 멈춰 비용은 없었다.
- 커밋백: 평가가 끝난 뒤 `git pull --rebase`가 "unstaged changes"로 거부됐다. 러너에서 `fetch_models.sh`가 추적 중인 모델 메타(JSON)·체크섬을 다시 써서 작업 트리가 더러워진 것. `--autostash`를 붙였고, 이미 끝난 실행의 아티팩트에서 결과만 커밋하는 복구 워크플로(`artifact-commit.yml`, 무료)를 추가해 $1짜리 재실행 없이 v1.3 결과를 회수했다.
- 교훈: 유료 단계 뒤에 오는 모든 단계는 실패해도 결과를 잃지 않도록(아티팩트 먼저, 커밋은 나중에·재시도 가능하게) 설계해야 한다.

## L15. 영상 파일과 정답의 프레임 번호가 1장 어긋남 (CAVIAR)
- 문제: CAVIAR의 MPEG 영상은 612프레임인데 정답은 611프레임(0~610)이었습니다. 영상을 그대로 쓰면 모든 사건이 1프레임씩 밀립니다.
- 수정: 정답과 번호가 맞는 JPEG 묶음을 받아 직접 H.264로 다시 만듭니다. 받을 때마다 "영상 프레임 수 = 정답 프레임 수"를 검사해 기록(`data/bench/manifest.json`)에 남깁니다. 2편은 사진이 정답보다 많아(사진 1장 누락 뒤 꼬리, 끝 3장) 정답 구간만 쓰고 그 사실을 기록에 적었습니다. 정답 파일이 3개로 서로 다른 1편은 제외했습니다.

## L16. 다운로드 프로세스가 메모리 부족으로 강제 종료됨
- 문제: MOT20-02(1080p 사진 2,782장)를 전부 풀어 메모리에 올리면 약 17GB가 필요해, 학습과 함께 돌던 다운로드가 OOM으로 종료됐습니다(학습은 살아남음). 그 전에는 서버가 수천 번의 범위 요청 중 연결을 끊어 두 번 실패했습니다.
- 수정: 압축된 JPEG만 메모리에 두고 한 장씩 풀어 ffmpeg로 넘깁니다. 파일별 재시도와 8개 동시 요청, 영상마다 기록 저장(중간에 죽어도 끝난 것은 남음)을 넣었습니다. 1080p 429장이 84초에 받아졌습니다(이전 방식은 실패).

## L17. 위에서 내려다본 사람을 못 찾는 문제 → 추가 학습
- 발견: 조정 분할 로비 영상에서 정답 상자는 사람을 정확히 감싸는데(좌표 확인), 기본 모델은 그 사람을 내지 않고 의자 쪽에 낮은 점수의 상자만 냈습니다. COCO 사진은 대부분 옆에서 찍은 사람이라 위에서 본 모습을 학습하지 못했습니다.
- 조치: 학습 분할로 추가 학습(D12). 조정 분할 로비에서 찾은 사건이 10건 중 2건 → 8건, 전체 시간당 잘못 울림 23.6 → 4.7.
- 덤으로 고친 것: 학습 결과 파일에 numpy 숫자가 섞여 `torch.load(weights_only=True)`(임의 코드 실행 방지)가 거부했습니다. 안전 모드를 끄지 않고, 저장할 때 일반 숫자로 바꾸도록 고쳤습니다.

## L18. 최종 측정 1회째가 결과 저장 직전에 중단 → 이유를 남기고 2회째
- 문제: 최종 분할의 MOT 영상에는 '판정 제외' 상자(사람 모양 방해물, 거의 가려진 사람)가 있습니다. 사람 찾기 AP 계산에서, IoU 0.5에서는 맞고 0.75에서는 안 맞는 상자가 제외 영역과 겹치면 기준마다 남는 상자 수가 달라지는데 점수 목록을 하나로 써서 IndexError가 났습니다. 첫 후보의 모든 영상을 처리한 뒤라 결과 파일은 하나도 저장되지 않았습니다.
- 처리: 기준별 점수 목록으로 고치고(COCO와 같은 처리) 회귀 테스트를 넣었습니다. 조정 분할(CAVIAR)에는 제외 상자가 없어 그 결과는 달라지지 않습니다. 최종 측정은 잠금 규칙대로 `--rerun-reason`에 이유를 적고 다시 돌렸고, 두 번의 시작 기록이 `docs/eval/bench/test_lock.json`에 남아 있습니다. 1회째 실행 중 첫 후보의 영상별 로그 몇 줄을 보았지만, 후보·구역·설정은 하나도 바꾸지 않았습니다.
- 교훈: 한 번만 재는 측정은 '끝까지 돌아간다'는 것을 같은 종류의 데이터(제외 상자가 있는 영상)로 미리 확인해야 합니다. 조정 분할에 MOT 영상이 없어서 이 경로가 처음 실행된 곳이 최종 측정이었습니다.
